# 引数を逆に渡しても、コンパイルは通ってしまう

いきなりですが、こんな関数を見たことはないでしょうか。

```go
func GetOrder(userID string, orderID string) (*Order, error)
```

呼び出すときに`userID`と`orderID`を逆に渡してしまっても、どちらも`string`なのでコンパイルは通ります。気づくのはテストで落ちたとき、悪くすると本番でエラーが出たときです。

「引数の順番を間違えないよう気をつける」のが対策になっているとしたら、それはコードがルールを守ってくれていない状態です。こういう問題への処方箋が、今回紹介する**ドメインモデリング**です。

:::message
この記事は「設計についてはこれから学ぶ」という方に向けて、ドメインモデリングとは何か、そして Go のコードでどう表現するかを解説します。DDD（ドメイン駆動設計）の難しい用語はいったん脇に置いて、今日から使える形に絞ってお伝えします。
:::

# ドメインモデリングってなに？

ドメインとは、ソフトウェアが対象とする業務領域のことです。EC サイトなら「注文」「商品」「在庫」、勤怠管理なら「出勤」「休暇」などがドメインの登場人物です。

ドメインモデリングとは、こうした業務の概念とルールをコード上のモデル（型と振る舞い）として写し取ることです。

ポイントは「データの入れ物」ではなく「概念とルール」を表現する点です。たとえば注文には、次のようなルールがあるはずです。

- 注文の金額は 1 円以上でなければならない
- 確定済みの注文には商品を追加できない
- メールアドレスは形式が正しくなければならない

プリミティブ型（`string`や`int`）のままコードを書くと、これらのルールは呼び出し側の`if`文としてあちこちに散らばります。ドメインモデリングでは、ルールを型そのものに閉じ込めます。

ドメインモデリングは DDD の文脈で語られることが多いですが、重厚な設計手法を導入しなくても、この考え方だけで日々のコードは十分に改善できます。ここからは Go での具体的な表現方法を 3 ステップで見ていきます。

# ステップ1: プリミティブ型に名前をつける

Go には Defined Type という機能があり、既存の型をもとに新しい型を定義できます。

```go
type UserID string
type OrderID string

func GetOrder(userID UserID, orderID OrderID) (*Order, error)
```

たったこれだけで、冒頭の「引数の取り違え」はコンパイルエラーになります。

```go
var userID UserID = "u_123"
var orderID OrderID = "o_456"

GetOrder(orderID, userID) // コンパイルエラー！
```

`UserID`と`OrderID`は、中身は同じ`string`でも Go のコンパイラは別の型として扱います。人間が気をつける代わりに、コンパイラがルールを守ってくれるようになりました。

型に名前がつくと、コードを読むときの情報量も増えます。`func Cancel(id string)`よりも`func Cancel(id OrderID)`のほうが、何を渡すべきか一目でわかりますね。

# ステップ2: コンストラクタで不正な値を弾く

名前をつけただけでは「メールアドレスは形式が正しくなければならない」といったルールはまだ守れません。そこで、値の生成をコンストラクタ関数に限定します。

```go
package domain

import (
	"errors"
	"strings"
)

type Email struct {
	value string
}

func NewEmail(v string) (Email, error) {
	if !strings.Contains(v, "@") {
		return Email{}, errors.New("メールアドレスの形式が正しくありません")
	}
	return Email{value: v}, nil
}

func (e Email) String() string {
	return e.value
}
```

ポイントは、フィールド`value`を小文字（非公開）にしていることです。パッケージの外からは`NewEmail`を通さないと値の入った`Email`を作れないため、**中身のある`Email`は常に検証済み**という状態を作れます。

ただし注意点がひとつあります。Go の仕様上、ゼロ値（`var e Email`や`Email{}`）だけはパッケージの外からでも作れてしまいます。コンストラクタで防げるのは「不正な値を入れること」までで、「未初期化のまま使うこと」は防ぎきれません。実務ではゼロ値の扱いに注意が必要です。

この効果は思った以上に大きいです。受け取る側の関数は「この値は正しいのか？」と疑う必要がなくなり、防御的な再チェックのコードが消えていきます。バリデーションのロジックも`NewEmail`の 1 箇所に集約されるので、ルールが変わったときの修正も一度で済みます。

こうした「値そのものに意味とルールを持たせた型」は、DDD では Value Object（値オブジェクト）と呼ばれています。

# ステップ3: 振る舞いをメソッドとして持たせる

最後に、「確定済みの注文には商品を追加できない」のような複数の値にまたがるルールを表現します。データとルールを 1 つの型にまとめ、操作をメソッドとして提供します。

```go
type Order struct {
	id     OrderID
	items  []OrderItem
	status OrderStatus
}

const maxOrderItems = 10

func (o *Order) AddItem(item OrderItem) error {
	if o.status != OrderStatusDraft {
		return errors.New("確定済みの注文には商品を追加できません")
	}
	if len(o.items) >= maxOrderItems {
		return errors.New("注文できる商品は10個までです")
	}
	o.items = append(o.items, item)
	return nil
}
```

ここでもフィールドはすべて非公開です。外部から`o.items = append(...)`と直接いじることはできず、必ず`AddItem`を通ることになります。つまり、**ルールを無視して注文を変更する手段が存在しない**わけです。

「注文には商品を 10 個まで追加できて、確定後は変更できない」という仕様を知りたければ、`Order`型の定義を見るだけで済みます。仕様がコードのどこにあるか探し回る必要はありません。

# Before / After で比べてみる

プリミティブ型のままのコードと、ドメインモデルを導入したコードを比べてみます。

| 観点 | プリミティブ型のまま | ドメインモデル |
| --- | --- | --- |
| 引数の取り違え | コンパイルが通ってしまう | コンパイルエラーで気づける |
| バリデーション | 呼び出し側ごとに散らばる | コンストラクタの 1 箇所に集約 |
| 業務ルール | サービス層の`if`文の海 | モデルのメソッドに凝集 |
| 仕様の調べ方 | コード全体を検索する | 型の定義を読めばわかる |

どのステップも Go の標準機能（Defined Type、非公開フィールド、メソッド）だけで実現できています。フレームワークもライブラリも不要で、明日のプルリクエストから試せるのがドメインモデリングの良いところです。

# まとめ: ここから先の話

この記事では、ドメインモデリングの考え方と、Go で表現するための 3 ステップを紹介しました。

1. プリミティブ型に名前をつけて、取り違えをコンパイラに検出させる
2. コンストラクタで不正な値を弾いて、検証済みの値だけを流通させる
3. 振る舞いをメソッドとして持たせて、ルールをデータのそばに置く

ただ、実際のプロジェクトに持ち込もうとすると、ここから先にたくさんの疑問が出てきます。

- 複数のモデルにまたがる整合性はどう守るのか（集約）
- DB への保存とドメインモデルをどう分離するのか（リポジトリ）
- パッケージ構成はどう切るのか、レイヤーはどこまで分けるのか
- トランザクションやドメインイベントはどこに書くのか

このあたりの「実務で詰まるポイント」は、続編として準備中の有料本で、サンプルアプリケーションを題材にじっくり解説する予定です。
