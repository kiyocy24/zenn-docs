# バズを狙う記事ネタの提案

直近のトレンドとバズっている記事を調査し、ユーザーが書ける記事ネタを提案します。

## 手順

### 1. 軸を決める

- 引数で分野・技術スタックが指定されていればそれを軸にする
- 指定がなければ、既存記事の topics(`articles/*.md` の frontmatter を確認。例: Go, GCP, Terraform, Docker, UUID)と執筆傾向(検証系・構築手順系)を軸にする

### 2. トレンド調査

WebFetch と WebSearch を併用して調査します。

**Zenn のトレンド**(WebFetch):

- `https://zenn.dev/api/articles?order=daily`(公開 API。JSON で title / topics / liked_count が取れる)
- `https://zenn.dev/`(トレンドフィード)
- 特定分野は `https://zenn.dev/topics/<topic>` も参照

:::message
実行環境によっては zenn.dev への直接アクセスがネットワークポリシーで 403 になります(リモート実行環境で確認済み)。その場合は WebFetch を粘らず、WebSearch(`site:zenn.dev` を含むクエリや「Zenn トレンド <分野>」)にフォールバックしてください。
:::

**直近の話題**(WebSearch):

- 対象分野の直近数週間のニュース: 新バージョンリリース、新サービス・新機能発表、話題になった障害・事例
- はてなブックマークのテクノロジーカテゴリ(`b.hatena.ne.jp/hotentry/it`)も補助的に参照

### 3. バズ要因の分析

収集した人気記事から「ウケている切り口」を抽出して整理します:

- 型の例: やってみた・検証系 / 比較系 / 失敗談・障害対応 / n 選まとめ / 新機能速報 / 意外な組み合わせ
- タイトルパターンといいね数の傾向(数値は**取得時点のもの**と明記する)

### 4. 記事ネタを 5〜7 個提案

各ネタに以下を添えます:

- **仮タイトル**(目を引く形)+ emoji 案
- **狙う読者**と「**なぜ今バズるか**」の根拠(参照したトレンド記事・ニュースへのリンク付き)
- **想定アウトライン**(見出し 3〜5 個)
- **ユーザーが用意すべきデータ・検証**(この記事の根拠として何が必要か)
- **バズ期待度**(高/中/低)と**執筆コスト**(かかる検証・作業の目安)

### 5. 引き渡し

ユーザーがネタを選んだら、そのネタのアウトライン下書き(見出し構成+各セクションで書くこと+必要データのリスト)を作り、そのまま `/write-article` に渡せる形で提示します。

## 注意事項

- **トレンドの模倣ではなく、ユーザー自身の実体験・検証データを載せられるネタを優先する**。既存記事の強みは一次情報(自分で測った・作った・運用した)にある
- 既にバズった記事の焼き直しは避け、「切り口を変える」「対象を変える」「深掘りする」で差別化する
- いいね数などの数値は取得時点のものと明記する
